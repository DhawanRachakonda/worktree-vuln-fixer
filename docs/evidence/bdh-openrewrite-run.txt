Windows 11, Copilot CLI 1.0.109, plugin 1.24.0, SUBSCRIBER_PERMISSION_MODE=allow-list (the wrapper .\mvnw.cmd is on the allow-list)
Fixture: a small hand-made Maven project (log4j-core/log4j-api 2.14.1, commons-text 1.9) and a hand-made report; not a vendor export.

## Run 1: before the rules were written down (session e4c4250f)
state=ERROR, 2 commits, no OpenRewrite attempt.
- The agent wrote ./mvnw.cmd (forward slash) and unquoted -Drewrite.x=y arguments. Copilot's command parser could not read them
  (hasParseErrors, allowMatchIdentifier null), so a headless allow-list refused them even with the wrapper allowed.
- It edited pom.xml by hand ("fix:" commits) and ended without .appmod/result.json, so the engine recorded ERROR.

## What changed after run 1
- engine prompt (prompts/default.md): mechanical changes go through OpenRewrite first; one simple command per call;
  write the wrapper as .\mvnw.cmd (backslash) and put every -D argument in double quotes; create report files with the file tool.
- kit: security-audit and security-fixer agents, openrewrite-recipes skill and docs/openrewrite.md carry the same rules.

## What this shows, and what it does not
- Shows: with the wrapper allowed and the commands written as the rules say, the default Copilot job takes the OpenRewrite path and
  the result is repeatable (recipe files are kept in .appmod).
- Does not show: that the agent always does so (it is not deterministic: run 1 failed, run 2 passed, nothing in between was sampled),
  a real Black Duck export, or the plugin's own orchestrator (its hook failed in this environment).
